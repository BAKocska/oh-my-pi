# What this probes

This is a conformance probe, not a port, and has no pi origin. It constructs one immutable `omp.ContextView` containing a pinned item, two ids deliberately touched by competing `thread_projection` handlers, a stale item, and ordinary survivors. Its smoke runs a small agent-side oracle with the application shape required by `docs/py/08-context.md`: fence the captured epoch, resolve and validate every operation against the original view, detect touched-id conflicts in fixed operation order, build a plan, and only then mutate the working copy.

The declared hook and its second handler-shaped contributor model two extensions in deterministic handler order; the frozen declaration registry permits only one handler per event/phase inside one extension. The earlier handler replaces `shared` and prunes `move`; the later contributor tries `DropParts(shared)` and `Reorder(move)`. The smoke invokes both and also mixes rejected and valid sibling operations, so dropping a whole patch cannot masquerade as per-op fail-open behavior.

## Conflict matrix

| Conflict | Documented behavior | Re-observed by `smoke()` |
|---|---|---|
| Two handlers touch the same ids | Cross-handler conflicts resolve by deterministic handler order first: the earlier handler's op is kept and the later handler's op is dropped (`docs/py/08-context.md:603-613`, “Chaining”). | Both later-handler operations are dropped independently; the earlier handler's replace and prune survive. |
| Required id is nonexistent or has left the live chain | An unknown-but-required id drops and journals only that op before mutation (`docs/py/08-context.md:1652-1656`, “Patch application”). | `Replace(missing)` and `DropParts(stale)` produce per-op `PatchRejected` diagnostics before the valid sibling prune materializes. |
| One operation repeats an id | A duplicate id is a validation failure for that op; it is dropped and journaled, never coalesced (`docs/py/08-context.md:408-411`, 2026-08-20 ruling). | The duplicate-id reorder is rejected before mutation and its valid sibling still applies. |
| `Prune` names an unknown id | Unknown ids are ignored for `Prune` (`docs/py/08-context.md:425-426`, “`omp.Prune`”). | The unknown prune target is ignored and diagnosed; the projection is otherwise unaffected by that op. |
| Operation targets `pinned` | The offending op is dropped and journaled; valid siblings continue (`docs/py/08-context.md:425-426,590-600`). | The pin survives; an unrelated valid prune from the same patch applies. |
| Earlier `Prune(id)` plus later `Reorder(id)` | Lists apply as `prune → drop_parts → replace → insert → reorder`, earlier-op-wins (`docs/py/08-context.md:403-410,1657-1660`, 2026-08-20 ruling). | Earlier prune wins and later reorder is dropped. |
| Earlier-handler `Replace(id)` plus later-handler `DropParts(id)` | `DropParts` is the fifth projection-only op and participates in the same conflict accounting (`docs/py/08-context.md:434-460`, 2026-08-20 ruling). Cross-handler order wins before op-class order (`docs/py/08-context.md:609-613`). | The earlier handler's replacement wins and the later handler's `DropParts` is dropped. |
| Compaction epoch advances while patch is in flight | Reject the whole patch before op validation with `ContextGone`, leave the projection untouched, journal the rejection, and proceed unpatched (`docs/py/08-context.md:1647-1651,1667-1668`, 2026-08-20 ruling). | `ContextGone` is raised before validation/materialization and the projection remains byte-for-byte unchanged. |

## Numbered findings — closure record

1. **Closed — rejected-patch scope.** The defect was contradictory whole-patch and per-op failure language. The in-body fix at `docs/py/08-context.md:590-600` now distinguishes whole-handler fail-open from per-op patch validation, and the failure table repeats the per-op rule at `docs/py/08-context.md:2096`. Agent Core now returns a `PatchOutcome` whose `dropped` entries retain each rejected op's input index and reason while valid siblings materialize. Re-observed in Rust: a rejected middle op leaves operations 1 and 3 applied, and rejected reorder/dedupe claims do not poison a later valid op.
2. **Closed — unknown-id handling.** The defect report overgeneralized required-id rejection to `Prune`. The in-body rule at `docs/py/08-context.md:425-426` preserves the intentional exception: an unknown prune id is ignored, while required ids for other operations are validated per `docs/py/08-context.md:1652-1656`. Re-observed: `Prune(unknown)` is ignored and diagnosed without rejecting its patch.
3. **Closed — `DropParts` semantics.** The defect was that the frozen carrier existed without a context-patch specification. The in-body fix at `docs/py/08-context.md:432-460` defines projection-only part removal, unknown/pinned rejection, duplicate handling, and conflict accounting; the resolution is recorded at `docs/py/08-context.md:2200`. Agent Core now clears `Message` and `ToolResult` parts during its existing single materialization pass while retaining the item and all metadata; pinned targets are rejected without mutation. Re-observed by the oracle: the earlier handler's accepted replacement claims `shared`, so the later handler's conflicting `DropParts(shared)` is dropped.
4. **Closed — duplicate ids.** The defect was no defined choice between rejection and coalescing. The in-body fix at `docs/py/08-context.md:408-411` requires pre-mutation rejection of the offending op, with the ruling recorded at `docs/py/08-context.md:2202`. Re-observed: `Reorder(ids=("tail", "tail"))` is rejected with `duplicate id`; valid siblings still apply.
5. **Closed — patch precedence.** The defect was that operation lists had no semantic order, leaving same-patch prune/reorder and other cross-list collisions ambiguous. The in-body fixes at `docs/py/08-context.md:403-410,609-613,1657-1660` stratify precedence: deterministic handler order first across patches, then `prune → drop_parts → replace → insert → reorder` and list order within one handler. The ruling is recorded at `docs/py/08-context.md:2204`. Re-observed: the earlier handler claims `move` with prune before the later handler's reorder is considered, so reorder is dropped.
6. **Closed — epoch fence specification.** The defect was that `ContextView.epoch` had no patch-application fence. Step 0 at `docs/py/08-context.md:1647-1651` and the closure at `docs/py/08-context.md:1667-1668` now require whole-patch `ContextGone` before validation, projection untouched, fail-open; the failure table confirms it at `docs/py/08-context.md:2097`. Re-observed: advancing the host epoch rejects the patch and leaves the snapshot identical.

## Agent Core closure

The Python frozen surface, this oracle, and Agent Core now conform to all six closures. Rust `apply_patches` validates every operation transactionally, reports each rejected operation for journaling, and continues with valid siblings. Its `DropParts` plan preserves tool-result details, error/useless/pruning/provider metadata, item props including `omp/tool-rev`, and message roles while removing only model-visible parts.

## Smoke

With the repository's frozen Python package on `PYTHONPATH`, call `await patch_conflict.smoke(ctx)` using any stub `omp.Context`. The result names all seven observation groups covering every matrix row. Every assertion is local and deterministic; no host, journal, network, or filesystem mutation is required.
